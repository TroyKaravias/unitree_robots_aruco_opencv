00 — Course Overview

Video goal: Introduce the course, set expectations, explain the final outcome, and establish the difference between reusable vision code and robot-specific control code.

Read this on camera

Welcome to the Unitree Robotics G1 and Go2 ArUco OpenCV course.

In this course, we are going to build a computer-vision system that allows a Unitree robot to recognize printed ArUco markers and react to them.

The core idea is simple: the robot camera sends us video frames, OpenCV searches those frames for an ArUco marker, Python reads the marker ID, and then our program maps that ID to a robot behavior.

The vision portion of the project is reusable. The robot connection and movement commands are robot-specific.

The Go2 path covers the full pipeline: camera feed, ArUco detection, marker-triggered actions, autonomous patrol, built-in obstacle avoidance, and corner recovery.

The G1 section covers the same ArUco and OpenCV concepts with its own connection, camera, and safe-action scripts.

By the end of the Go2 section, the robot will be able to patrol, detect marker IDs zero through four, perform mapped actions, and use marker zero as the primary stop marker.

  2. Show printed marker examples for IDs 0 through 4.
  3. Show a short preview clip of the Go2 detecting a marker and responding.
  4. Display the course flow diagram: camera feed → OpenCV detection → marker ID → Python behavior mapping → robot command layer.

02 — What Is an ArUco Marker?

Video goal: Explain what ArUco markers are and why they are useful for robotics.

Read this on camera

An ArUco marker is a square visual marker made from a black border and an internal binary pattern.

Each valid pattern represents a numeric marker ID.

To a person, two markers may look very similar. To OpenCV, the internal black-and-white pattern identifies exactly which marker is being shown.

ArUco markers are useful because they are inexpensive, easy to print, and fast for a camera to detect.

In this course, we use them as visual command signs. A robot can see a marker, identify its number, and select a matching behavior.

The marker itself does not contain a robot command. Our Python code decides what each marker means.

What to show on screen

  1. Hold up or display marker IDs 0, 1, 2, 3, and 4.
  2. Zoom in on the black border and internal grid.
  3. Place two markers side by side and point out that their patterns differ.
  4. Show the marker-to-action table used later in the course.

Instructor and safety notes

  • Avoid overcomplicating this lesson with pose estimation.
  • Emphasize that the ID-to-action mapping is chosen by the programmer.

03 — ArUco Dictionaries and Marker IDs

Video goal: Explain DICT_4X4_50 and why the generator and detector must use the same dictionary.

Recording flow: read the left panel, run the matching command(s) on the right, verify the result, then continue downward.
Say this while recording

On-camera script

ArUco markers are organized into dictionaries.

A dictionary defines the marker grid size and the collection of valid marker patterns.

For this course, we use OpenCV's DICT_4X4_50 dictionary.

The 4X4 portion means the internal marker pattern uses a four-by-four binary grid.

The 50 means the dictionary contains marker IDs from zero through forty-nine.

The complete course uses IDs zero through eight; the Go2 and G1 lessons use different subsets of those markers.

The marker generator and the marker detector must use the same dictionary. If we generate a marker from one dictionary and try to detect it with another, detection may fail.

05 — What Is OpenCV?

Video goal: Introduce OpenCV's role in the project without overwhelming beginners.

Read this on camera

OpenCV is the computer-vision library that processes the robot's camera frames.

In this project, OpenCV receives an image, searches for ArUco marker corners, identifies valid marker IDs, and lets us draw boxes and labels on the display.

OpenCV does not control the robot by itself.

It only gives our Python program information about what the camera sees.

Our Python code then decides whether to print an ID, wait for confirmation, apply a cooldown, or send a robot command.

09 — Marker Confirmation and Cooldowns

Video goal: Explain how confirmation counts and cooldown timers prevent false or repeated triggers.

Read this on camera

A real camera stream contains noise, blur, and frames where a marker may only be visible briefly.

If we trigger an action from a single frame, the robot may react to an unstable or accidental detection.

A marker confirmation count requires the same marker to be detected across multiple frames before the action is accepted.

A cooldown timer prevents the same action from firing repeatedly while the marker remains in view.

Together, confirmation and cooldown logic make the system more stable and predictable.

The exact values can be tuned. Higher confirmation counts reduce accidental triggers but may make the robot respond more slowly.

What to show on screen

  1. Open the variables controlling confirmation and cooldown.
  2. Show the counter increasing while a marker remains visible.
  3. Hold the marker in view after triggering and explain why the action does not repeat immediately.
  4. Remove and reintroduce the marker after the cooldown.

Instructor and safety notes

  • Use the exact variable names from the current script during recording.
  • Avoid claiming a specific confirmation number unless it matches the file being recorded.

12 — Stronger Go2 Corner Recovery

Video goal: Explain why the robot can become stuck and how backup/turn recovery improves patrol behavior.

Read this on camera

Built-in obstacle avoidance may stop the robot near a wall or corner, but stopping alone does not always help it escape.

The stronger recovery behavior adds a sequence designed to move the robot away from a blocked position.

A typical recovery sequence is: stop, back up, turn, scan, and then resume patrol.

The project also includes logic for a second recovery when two recoveries happen close together.

The second recovery uses a different or smaller turn so the robot does not repeat exactly the same failed path.

This is behavior-level recovery. It does not replace full mapping or advanced navigation.

14 — G1 Adaptation Overview

Video goal: Explain how the G1 differs from the Go2 and describe the G1-specific architecture that is now fully working.

Read this on camera

The G1 humanoid reuses the same ArUco and OpenCV detection pipeline as the Go2.

The dictionary, detector parameters, confirmation count, and cooldown logic all transfer directly. DICT_4X4_50, three-frame confirmation, and a four-second cooldown work the same way on both robots.

The robot-specific layer is completely different from the Go2.

The G1 camera is an Intel RealSense D435i accessed directly through V4L2 on the onboard Jetson NX. There is no WebRTC connection. The camera appears as /dev/video4.

Robot commands go through two compiled binaries on the Jetson: the loco client for locomotion state transitions and the arm action binary for built-in gestures. Both use CycloneDDS for communication with the robot body.

The G1 scanner runs headless on the Jetson and serves a browser-based MJPEG stream at port 8080. You open the stream on any device on the same network. No OpenCV window or laptop is needed once the scanner is running.

An auto-restart monitor script keeps the scanner alive even if it exits unexpectedly.

What to show on screen

  1. Show the scripts/g1 folder in the repository.
  2. Compare the Go2 WebRTC path with the G1 V4L2 plus browser-stream path.
  3. Show the browser stream at http://192.168.123.164:8080/ with the camera feed and log panel visible.

Instructor and safety notes

  • Go2 WebRTC commands and connection code are not compatible with the G1. Use only the G1-specific scripts in scripts/g1.
  • A realsense2_camera_node ROS process starts automatically on the Jetson at boot and holds the camera device. The scanner script detects and kills it automatically on startup.
Suggested transition: "Now that we understand the G1 architecture, we can connect and start the scanner."

17 — G1 Marker-Controlled Actions

Video goal: Demonstrate the complete G1 marker-to-action mapping and the correct workflow from rest through standing to gestures.

Read this on camera

The G1 has nine mapped marker IDs, zero through eight.

Markers zero and one are safety controls. Marker zero cuts all motor torque and the robot collapses. Use it only when the robot is already on the floor. Marker one enables damping mode, the safe compliant resting state. Always scan marker one first before any other action.

Marker two is the stand-up sequence. It sends stand-up to bring the robot to FSM state 4, waits up to ten seconds for the robot to physically rise, then sends start to transition to FSM 500, locked standing. The full sequence takes about twelve seconds. The browser stream may restart briefly during this transition and recover automatically.

Marker three enables walking and running mode from locked standing. It sends --start first to ensure FSM 500, then calls --switch_move_mode=true, which is the software equivalent of pressing R2+A on the physical controller. The robot then walks freely.

Markers four through eight trigger built-in arm gestures using the Unitree arm action binary. These require the robot to be in locked standing mode, FSM 500. Scan marker two first to reach that state.

  5. Scan marker 1 to return to damping before ending the demonstration.

On-camera script

BotBrain runs its ROS 2 environment inside Docker.

From the Jetson host, enter the bringup container and source the installed BotBrain workspace.

The controller publishes a Unitree WirelessController message on the wirelesscontroller topic.

The verified key mask for L1 plus Y is 2050, and the verified mask for L2 plus Y is 2080. These are the planned BotBrain ROS 2 integration keybinds.

The deployed onboard WebRTC script reads the controller via rosbridge at localhost port 9090. The confirmed working keybinds are: D-pad Down plus A (bitmask 16640) to start autonomous patrol, D-pad Down plus B (bitmask 16896) to stop it, D-pad Down plus X (bitmask 17408) to kill and immediately restart the script via the monitor, and D-pad Down plus Y (bitmask 18432) to kill the script and block auto-restart until X is pressed again.

Our intended BotBrain behavior is L1 plus Y to enable autonomous search and L2 plus Y to disable it.

Disabling autonomy must only stop the custom velocity command and return control to normal manual walking. It must not call Damp, Sit, StandDown, or another posture command.

BotBrain routes multiple velocity sources through twist_mux. Manual joystick control has priority 100. The candidate custom autonomy input, cmd_vel_nipple, has priority 99, so normal manual control remains one priority level higher.
